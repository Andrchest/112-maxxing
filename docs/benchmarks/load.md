# Нагрузочный тест: 20 / 50 / 100 обучаемых ДДС + инструктор, скорость записи в БД

Этап I7 E48. Что проверяется:

- ТЗ ¶159 (REQ-2137): «Время отклика интерфейса не более 2 секунд при нагрузке до 100
  пользователей»;
- ТЗ ¶164 (REQ-2141): «Скорость записи данных в БД не менее 100 операций в секунду»;
- пункт 8 владельца: не меньше 20 одновременных сессий обучаемых и инструктор, без видеокарты.

Скрипты: `benchmarks/benchmark_load.py`, `benchmarks/benchmark_db.py`, стенд
`benchmarks/_load_stack.py`. Запуск: `make bench-load` (по умолчанию 20, 50 и 100 обучаемых по
очереди) и `make bench-db`. Результаты, на которые ссылается этот документ, сжаты gzip и лежат в
`docs/benchmarks/results/`:
`load-DEV_3060TI-20260929T104434558Z.json.gz` (20/50/100),
`load-DEV_3060TI-20260929T104811784Z-tick1000.json.gz` (50, такт 1000 мс),
`db-DEV_3060TI-20260929T103436402Z.json.gz` (запись в БД).

## 1. Методика

**Стенд.** Каждый запуск поднимает свой отдельный стенд и в конце удаляет его (`docker compose
down -v`, backend останавливается по сохранённому PID). Проект compose `sim112load`, PostgreSQL 16
(данные на томе docker, не в памяти) и Redis 7 только на 127.0.0.1, порты 35432 и 36379. Порты
демо (5180/8120/25432/26379/17880), владельца (8000/8001/8011/8012/5000) и тестового стенда
скрипт не займёт: он откажется запускаться. Настоящий backend (`uvicorn`, один процесс, как в
`backend/Dockerfile`) работает на порту 18190. Распознавание, синтез речи, LLM и телефония в нём
подменены заглушками (`fake`), видеокарта не используется. Фоновый такт сессий (D7) включён с
заводским `SIM_SIM_TICK_MS=500`. Схема создаётся через `alembic upgrade head`, администратор через
`app.tools.seed_users` (пароль случайный, передаётся только через переменную окружения),
сценарии через `app.tools.import_scenarios`.

**Что делают виртуальные пользователи.** Всё идёт через настоящие HTTP API и WebSocket продукта.

1. Подготовка (время подготовки не входит в оценку по ¶159). Администратор создаёт инструктора и
   N обучаемых. Инструктор создаёт одно занятие: режим `SINGLE_ROLE`, карточка
   `GENERATED_CARD`, ДДС в режиме памятки `MEMO_STATUSES`, сценарий `street-rubbish-fire`, по 2
   карточки на каждого обучаемого. Все карточки приходят в момент 0 и сразу привязаны к своему
   обучаемому. Затем инструктор запускает занятие, и все 2×N сессий становятся `ACTIVE` сразу.
2. Обучаемые (N одновременно, входы растянуты на 10 с). Каждый входит в систему, запрашивает
   профиль и каждые 3 с обновляет «Список происшествий», как это делает интерфейс. По каждой своей
   карточке обучаемый:
   - открывает снимок сессии и WebSocket (`resume` с 0), читает службы и уведомления;
   - работает с карточкой как консоль памятки: у Службы 101 последовательно ставит «Принята»
     (номер наряда и комментарий), «Выезд», «Прибытие», «Работа», «Завершена» (с комментарием);
     остальным службам ставит «Не принята» с обязательным комментарием;
   - ставит отметки «ЧС/ЧП» и закрывает происшествие.

   Между действиями обучаемый «думает» случайные 1–3 с (генератор с фиксированным seed). После
   каждого статуса список служб перечитывается, как консоль делает по событию WebSocket.
3. Инструктор каждые 3 с опрашивает доску занятия (`getLesson`) и обзор одной карточки
   (`getInstructorSessionOverview`), перебирая карточки по кругу. WebSocket первой карточки у него
   открыт всё время.

**Что измеряется.**

- По каждому запросу: время ответа (p50, p95, p99, максимум по каждой операции), код ответа
  (любой не-2xx или сетевая ошибка считается ошибкой) и размер ответа.
- Задержка доставки события по WebSocket: время получения у клиента минус `timestamp_utc`
  события. Клиенты и сервер работают на одной машине, поэтому часы общие.
- Время подключения WebSocket до `resume_complete`.
- RSS и загрузка CPU процесса backend (по `/proc` сохранённого PID).

Для ¶159 учитываются все запросы обучаемых и инструктора («интерактивные»). Цель: p95 ≤ 2000 мс
и ни одной ошибки.

**Запись в БД (¶164).** Работают N писателей одновременно, у каждого своя начатая сессия с
происшествием. Каждый пишет M = 100 событий через `SqlAlchemyUnitOfWork.events.append`, одно
событие на транзакцию. Это тот же путь, что у каждой команды обучаемого: блокировка строки
сессии §20.8, пересчёт статуса карточки (§70.3.5), INSERT и COMMIT с ожиданием записи WAL на диск
(`synchronous_commit` по умолчанию). Результат: число записей в секунду и задержка одной записи.
Стенд отдельный: проект `sim112loaddb`, порты 35442 и 36389.

## 2. Машина

Intel Core i5-12500 (12 потоков), 31 ГБ ОЗУ. Swap во время замеров был почти полностью занят
другими процессами владельца. Диск: `pg_test_fsync` на томе docker показывает **≈ 79
`fdatasync`/с (≈ 12,7 мс на одну операцию)**. Это медленный диск, и именно он ограничивает число
фиксаций транзакций в секунду (см. §4). Клиенты и сервер работали на одной машине, поэтому сеть
не измерялась. Параллельно работали демо и чужие процессы. Разброс между повторами одного размера
занятия ±30 % по p95.

**Вердикт по ¶159.**

- 20 обучаемых и инструктор: **p95 = 1,3 с, цель выполнена**. При этом 2,9 % запросов дольше 2 с:
  это отдельные всплески, максимум 6,3 с.
- 50 обучаемых: p95 = 2,8 с, цель **не выполнена**.
- 100 обучаемых: p95 = 4,5 с, цель **не выполнена**.

Начиная примерно с 40 активных сессий единственный процесс backend загружает ядро на 100 %.

88 / 354 / 2 921 при N=50, 102 / 555 / 2 925 при N=100. При N=100 четыре подключения WebSocket из

при этом закрыты: команды идут по HTTP.

Время запуска занятия `startLesson` (все карточки создаются и запускаются в одном запросе):
2,6 с для 40 карточек, 20,4 с для 100 и **94,8 с для 200**.

**Вердикт по ¶164: цель 100 записей/с выполнена при параллельной записи** (179 и 235 записей/с).
Один последовательный писатель упирается в `fdatasync` этого диска (≈ 20 мс на фиксацию) и даёт

запись на диск.

При 100 писателях пул соединений (20 + 10) меньше числа писателей. Отдельные записи ждут
соединение до 25 с: это максимум в таблице. В предыдущем прогоне того же размера 40 записей из
10 000 не дождались соединения за 30 с пула.

### 3.4 Такт 1000 мс вместо 500 (опыт, N=50)

p95 = 2 788 мс против 2 810 мс при 500 мс, CPU по-прежнему 100 %. Реже тактовать бесполезно:
каждая команда обучаемого всё равно выполняет свой такт сразу. Узкое место не в частоте фоновых
тактов, а в работе, которую делает каждый запрос.

## 4. Что найдено и исправлено

Все три исправления небольшие и локальные, миграция не понадобилась: горячие чтения идут по
`session_id` и `seq_no`, эти поля уже в индексах. Числа «до» относятся к промежуточным прогонам,
их JSON в `docs/benchmarks/results` не копировался.

1. **Пул соединений заканчивался уже при 20 обучаемых.** Автоматика стадии ДДС
   (`app/application/dds/stage_automation.py`) спрашивала сценарных исполнителей
   (`ScenarioResponderScripts`, у него своя единица работы, то есть второе соединение) изнутри
   своей транзакции. Двадцать сессий в режиме памятки тактуют одновременно, каждая держала одно
   соединение и ждала второе. В журнале было `QueuePool limit of size 5 overflow 10 reached …
   timeout 30.00`, `startLesson` не ответил за 30 с, прогон не состоялся. Исправление:
   исполнителей спрашивают до открытия транзакции и передают внутрь. Ответ кэшируется на сессию:
   версия сценария сессии не меняется, а версия сценария неизменяема (D4).
   После исправления N=20 прошёл без ошибок, но p95 = 8,2 с и максимум 25 с.
2. **Холостой такт ждал записи на диск.** Такт сессии (`TickSession`) и автоматика ДДС в режиме
   памятки делали COMMIT, даже если ничего не записали. Обе транзакции берут блокировку строки
   сессии (§20.8), поэтому у транзакции есть номер и COMMIT ждёт `fdatasync`. Получалось по две
   фиксации на каждую активную сессию дважды в секунду. На диске с ≈ 80 `fdatasync`/с в эту
   очередь вставали команды обучаемых: `pg_stat_activity` показывал COMMIT в ожидании
   `WALWrite` до 5,8 с.

   Исправление: холостой такт завершается без COMMIT, единица работы откатывает его на выходе.
   Так уже работали `AdvanceCallFlow` и `AdvanceDdsCalls`. Автоматика фиксирует транзакцию, если
   записан шаг сценария, событие срока или звонок бригады. Ещё один случай: перенос сроков выставил
   службе липкий признак `accept_missed`, единственную запись без события; это проверяется
   повторным чтением служб в той же транзакции.

   При N=20 p95 снизился с 8,2 до 1,4 с, максимум с 25 до 4,3 с.
3. **Пул 5 + 10 был мал.** Соединения сверх пяти закрывались при возврате в пул и открывались
   заново, каждый раз с проверкой пароля SCRAM (PBKDF2 на чистом Python в asyncpg). Добавлены
   настройки `SIM_DB_POOL_SIZE` (20) и `SIM_DB_MAX_OVERFLOW` (10), описаны в `.env.example`.
   При N=50 p95 снизился с 7,1 до 4,4 с в том же прогоне, `startLesson` ускорился с 41,6 до 26,6 с.

Сам стенд тоже поправлен. Проверка здоровья PostgreSQL идёт по TCP: временный сервер
инициализации образа слушает только сокет, и миграция иногда получала сброс соединения. Клиент
закрывает простаивающие keep-alive соединения через 4 с, раньше uvicorn (5 с), как это делает
браузер.

## 5. Что не исправлено: слишком крупно для этого этапа

- **Цена такта.** Каждый такт активной сессии (раз в 500 мс и после каждой команды) делает
  следующее:
  - трижды читает сессию;
  - читает документ сценария, мир, представление звонящего, ресурсы и состояние движка;
  - читает **весь** журнал событий сессии (`load_world_state`);
  - выполняет ещё запросы трёх обработчиков.

  Из-за этого один процесс API упирается в CPU примерно с 40 активных сессий. Что можно сделать:
  свёртка журнала по приращениям, кэш неизменяемого документа сценария, запуск нескольких
  процессов API. Раннер уже умеет делить сессии через блокировки в Redis, но несколько процессов
  здесь **не проверялись**: пробный запуск `uvicorn --workers 4` на стенде не поднялся за 90 с, и
  причину я не разбирал.
- **`startLesson` запускает все карточки в одном запросе:** 95 с для 200 карточек. Браузер или
  прокси могут оборвать такой запрос.
- **Размер ответов.** Обзор инструктора весит ≈ 380 КБ: у каждой службы повторяются `field_specs`
  карточки, по ≈ 57 КБ. Снимок сессии и ответ `setDdsCardMarks` весят по 62–64 КБ. Чтобы это
  исправить, нужно менять контракт (`openapi.yaml`) и фронтенд.
- **Журнал аудита.** На каждый запрос пишется строка аудита с синхронным COMMIT, то есть ещё одна
  запись на диск на каждый запрос. Ослабить это (асинхронная фиксация, запись пачками) значит
  решить, насколько журнал аудита должен переживать сбой PostgreSQL.
- **Режим подбора сил (picker).** `TickSession.resolution_condition_met` в состоянии `WORKING`
  всё ещё открывает единицу работы изнутри транзакции автоматики. Это та же вложенность, что в
  п. 4.1, но нагрузка в режиме памятки её не задевает.

Вопрос владельцу: Q-I7-E48-1 в `docs/owner-decisions.md`.

## 6. Ограничения

- Всё работает на одной машине: клиенты отнимают CPU у сервера, сеть не измерялась. Время
  отрисовки в браузере в замер не входит.
- Голос подменён заглушкой. Нагрузки от распознавания и синтеза речи, LiveKit и SIP здесь нет;
  нагрузка от одновременных звонков описана в `voip.md`.
- Сценарий один (`street-rubbish-fire`, памятка) и работает только ДДС. Режим оператора 112 и
  подбор сил не нагружались.
- Диск машины медленный (≈ 80 `fdatasync`/с), а swap занят. На сервере с SSD числа по §3.1 и §3.3
  будут лучше, но насколько, здесь не измерено.
- Между повторами разброс ±30 % по p95: на машине параллельно работали демо и другие задачи.
