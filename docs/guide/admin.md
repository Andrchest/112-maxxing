# Руководство администратора

См. также [README.md](README.md) — оглавление раздела и общие ограничения стенда, и
[../RUNBOOK.md](../RUNBOOK.md) — операционные процедуры (старт/стоп, preflight, сброс демо-данных,
устранение неполадок), которые дополняют этот раздел.

Администратор видит те же разделы, что преподаватель («Занятия», «Сессии», «Статистика»,
«Сценарии», «Материалы» — см. [instructor.md](instructor.md)), плюс собственный раздел
«Администрирование» (`/admin`), доступный только роли `ADMIN`. Он состоит из шести вкладок:
«Пользователи», «Журнал», «Статистика», «Нагрузка», «Ошибки», «Оповещения». Справа от заголовка —
кнопка «Экспорт настроек (XML)» (см. [«Экспорт и импорт настроек»](#экспорт-и-импорт-настроек-xml)
ниже).

## Пользователи

Вкладка «Пользователи»: список учётных записей (логин, имя, роль, статус, дата создания) с
поиском по логину, фильтром по роли и чекбоксом «Показывать заблокированных».

- **«Создать пользователя»** — логин, отображаемое имя, роль (`TRAINEE`/`INSTRUCTOR`/`ADMIN`),
  пароль.
- **«Заблокировать» / «Разблокировать»** — блокировка не удаляет учётную запись и её историю.
- **«Сбросить пароль»** — новый пароль для входа.
- **«Скачать профиль (JSON)»** — выгрузка результатов конкретного стажёра тем же файлом, что
  доступен ему самому в «Истории» (см. [trainee.md](trainee.md#история)).

Ограничения (проверяются на сервере, форма лишь отражает ответ): нельзя сменить роль или
заблокировать собственную учётную запись («Нельзя изменить роль или заблокировать собственную
учётную запись.»); в системе должен остаться хотя бы один активный администратор («В системе
должен остаться хотя бы один активный администратор.»); логин должен быть уникален («Пользователь
с таким логином уже существует.»).

## Журнал

Вкладка «Журнал» — таблица аудита действий: «Время», «Пользователь» (логин и имя, роль по-русски
под ними; у неудачного входа — логин, под которым пытались войти, с пометкой «попытка входа под
этим логином»), «Действие» (например, «Успешный вход», «Неудачный вход», «Доступ запрещён»,
«WebSocket-подключение», либо метод и путь HTTP-запроса), «Запрос», «Статус», «Результат» («ОК» /
«Отказано» / «Ошибка»), «IP-адрес». Фильтр по действию («Любое действие» или конкретное), по
диапазону дат («С даты» / «По дату (не включая)»); «Следующая страница» — более ранние записи.
Каждое изменяющее действие в системе (создание занятия, изменение статуса службы, выдача отчёта,
вход и т. д.) должно быть здесь.

## Статистика (нагрузка на стенд)

Вкладка «Статистика» раздела «Администрирование» — не путать со «Статистикой обучаемых»
преподавателя ([instructor.md](instructor.md#статистика-рейтинг-csv)): здесь — использование
самого стенда по дням («Дата», «Входы», «Сессии», «Занятия», «Активные пользователи») с фильтром
по датам.

## Нагрузка

Вкладка «Нагрузка» — текущие показатели сервера, обновляются каждые несколько секунд: время
снятия показаний, процессор, память, диск, видеопамять. Показатель, который сервер не смог
прочитать, отображается как «нет данных» — никогда как «0», чтобы не читаться ложным нулевым
значением.

## Ошибки

Вкладка «Ошибки» — объединённый список: записи из журнала сервера, события `MODEL_ERROR` сессий и
критические отказы моделей (`INFERENCE_FATAL`), от новых к старым, с фильтром по датам. Колонки:
«Время», «Источник» («Журнал сервера» / «Ошибка модели» / «Критический отказ модели»),
«Сообщение», «Сессия» — если запись связана с конкретной сессией, ссылка «Отчёт» ведёт в её отчёт.

## Оповещения

Вкладка «Оповещения» — активные предупреждения, требующие внимания администратора: «Критический
отказ модели», «Резервная копия устарела», «Резервное копирование не выполнено», «Повторные
неудачные входы» — с временем, «с которого» оповещение активно. Число активных оповещений видно
также значком у правого края шапки на любой странице администратора. Здесь же — блок «Резервное
копирование»: время последнего успешного backup'а, статус («ОК»/«Ошибка»), размер базы данных и
записей (см. ниже).

## Резервное копирование и восстановление

Backup — по расписанию (`SIM_BACKUP_INTERVAL_SECONDS`, по умолчанию раз в сутки) через compose-
сервис `backup`; хранится `SIM_BACKUP_KEEP` (по умолчанию 14) последних копий. Из интерфейса
резервное копирование только **наблюдается** (вкладка «Оповещения» выше показывает, когда была
последняя копия и её статус) — запуск и восстановление выполняются с сервера:

```
make backup-now         # снять резервную копию прямо сейчас, не дожидаясь расписания
make backup-verify      # проверить backups/last.json: свежая ли копия и успешная ли
make restore FILE=./backups/sim-<ts>.dump RECORDINGS=./backups/recordings-<ts>.tar.gz
```

`make restore` останавливает `backend`, восстанавливает базу данных и (если указано) записи
разговоров, затем запускает `backend` снова; `RECORDINGS=` можно опустить, чтобы восстановить
только базу. Подробности и пример полного цикла — «Резервное копирование» и «Восстановление» в
[../RUNBOOK.md](../RUNBOOK.md).

## Экспорт и импорт настроек (XML)

**Экспорт** — из интерфейса, кнопка «Экспорт настроек (XML)» вверху раздела «Администрирование»:
скачивает `settings.xml` с действующими настройками стенда (после наложения `.env` и профиля).
Секреты (пароли, ключи, токены, строки подключения к БД/Redis с учётными данными) в файл не
попадают вовсе — не маскируются, а полностью отсутствуют.

**Импорт — только из командной строки**, в интерфейсе кнопки для этого нет:

```
make settings-import FILE=./settings.xml                    # пишет infra/.env.settings
make settings-import FILE=./settings.xml OUT=./other.env     # другой путь назначения
```

Файл проверяется (схема, только известные имена `SIM_*`, ни одного секрета, каждое значение — по
типу настройки); при любой ошибке ничего не записывается и не изменяется. Применение изменений
зависит от того, как запущен стенд, — подробности в разделе «Экспорт и импорт настроек» в
[../RUNBOOK.md](../RUNBOOK.md).

## HTTPS и сертификаты

Телефон и микрофон в браузере работают только в защищённом контексте (https или `localhost`) —
без этого стажёр не сможет ни звонить, ни говорить. Для класса из нескольких компьютеров стенд
поднимает свой TLS-узел (Caddy) с локальным центром сертификации:

```
infra/scripts/make-certs.sh --ip <LAN-адрес сервера> --host <имя сервера>   # once per server
```

Скрипт печатает отпечаток (SHA-256/SHA-1) корневого сертификата `ca.crt` — его, и только его,
нужно установить на каждый компьютер класса (инструкции для Windows/Firefox/Linux — раздел «HTTPS
в классе» в [../RUNBOOK.md](../RUNBOOK.md)). После этого в `.env` выставляется
`COMPOSE_PROFILES=tls` и `SIM_LIVEKIT_PUBLIC_URL`, и `make up` поднимает узел `edge`; компьютеры
класса открывают `https://<адрес сервера>` вместо прежних портов.

## SIP

Свой SIP-сервер тренажёра (не привязан к внешнему провайдеру и не требует оборудования) даёт
стажёру в роли ДДС звонить и принимать звонки на обычном софтфоне вместо браузерного виджета
(см. [trainee.md](trainee.md#звонок)). Управление — с сервера, интерфейса в веб-приложении нет:

```
docker compose -f infra/docker-compose.yml --env-file .env --profile sip up -d sip-gateway
```

Обязательная настройка в `.env`: `SIM_SIP_PASSWORD` (пароль по умолчанию для регистрации),
`SIM_SIP_REALM` (по умолчанию `sim112`), `SIM_SIP_GATEWAY_SECRET` (служебный секрет между шлюзом и
backend). Имя пользователя SIP-аккаунта — логин стажёра; свой пароль для конкретного пользователя
задаётся командой `uv run python -m app.tools.set_sip_password --username <логин>`. Проверка
работы шлюза, список занятых портов и разбор кодов ошибок (403/404/486/503…) — раздел «SIP
gateway» и «SIP-телефон — рабочее место ДДС на софтфоне» в [../RUNBOOK.md](../RUNBOOK.md).
